Candidate 1 — Collapse the Quiz Pipeline into a Deep Quiz Module

Strong ✅ Validated via prototype
ports & adapters high leverage improves locality

Files

  • quiz_engine/quiz_service.py
  • quiz_engine/quiz_models.py
  • learning_service/__init__.py
  • state_core/scoring_engine.py
  • api_layer/routes.py

Problem

Quiz pipeline is shallow across 4 modules: QuizService manages sessions in-memory, LearningService coordinates events, ScoringEngine scores answers, Router translates HTTP. Interface surface nearly matches implementation — no deep module owns the quiz lifecycle.

After — Deep Quiz Module

flowchart LR
  Router[Router] --> QuizModule[QuizModule
deep]
  QuizModule --> EventStore[(EventStore)]
  QuizModule --> KeyStore[SealedAnswerKeyStore]
  classDef deep fill:#0f172a,color:#e2e8f0,stroke:#22d3ee,stroke-width:2px;
  classDef iface fill:#ecfeff,stroke:#22d3ee;

Solution

Fuse QuizService, quiz session logic, quiz item persistence, and scoring into a single deep QuizModule. The module owns the quiz lifecycle end-to-end. Only one public interface: start, answer, complete, summary. Router calls the interface; implementation details (event store, key store, scoring) are private.

Prototype: quiz_engine/quiz_module_prototype.py — run with python -m quiz_engine.quiz_module_prototype

Wins

  • ✅ Tests hit one interface
  • ✅ Scoring logic stops leaking
  • ✅ Delete 3 shallow wrappers
  • ✅ Locality: bugs concentrate in quiz module
  • ✅ Leverage: one interface, N call sites
  • ✅ Interface shrinks; implementation absorbs wrappers

Candidate 2 — Deepen the Content Pipeline: Fuse ContentService + LearningService Lesson Events

Worth exploring
in-process medium leverage

Files

  • content_engine/content_service.py
  • content_engine/content_models.py
  • learning_service/__init__.py
  • state_core/event_models.py

Problem

ContentService rebuilds lessons from events on init, but also maintains its own in-memory Lesson/Section models. LearningService emits LessonSectionCommittedEvent. Two modules hold lesson state — ContentService for queries, LearningService for events. The seam leaks: ContentService._rebuild_from_events() re-reads the event log on every instantiation.

After — Deep Content Module

Solution

Merge ContentService into LearningService (or a new ContentModule). Lesson/Section models become private. Event log remains the single source of truth; projections compute lesson state on demand. One module owns the content lifecycle: create, commit section, list, delete.

Wins

  • ✅ Eliminates dual lesson state
  • ✅ _rebuild_from_events() disappears
  • ✅ Locality: content bugs in one module
  • ✅ Interface shrinks; implementation absorbs projection logic

Candidate 3 — Collapse the Delivery Engine into the Feedback Seam

Speculative
local-substitutable

Files

  • delivery_engine/feedback_service.py
  • delivery_engine/delivery_models.py
  • api_layer/routes.py

Problem

DeliveryEngine is a single-class FeedbackService that transforms ScoreResult into FeedbackMessage. It has one caller (Router). The interface (FeedbackService.score_feedback) is nearly as complex as the implementation. Only one adapter exists (the real one) — no test double justifies the seam.

Before — Single-adapter seam

flowchart LR
  Router[Router] --> FeedbackSvc[FeedbackService]
  FeedbackSvc --> LearningSvc[LearningService]
  classDef shallow fill:#f8fafc,stroke:#94a3b8,stroke-dasharray: 4 4;
  class FeedbackSvc,LearningSvc shallow

After — Inline feedback logic

flowchart LR
  Router[Router] --> LearningSvc[LearningService]
  LearningSvc --> ScoreResult[score_feedback
pure fn]
  classDef deep fill:#0f172a,color:#e2e8f0,stroke:#22d3ee,stroke-width:2px;
  classDef iface fill:#ecfeff,stroke:#22d3ee;
  class LearningSvc deep
  class Router iface

Solution

Inline the feedback transformation into LearningService.submit_and_score_answer() as a pure function. Remove DeliveryEngine entirely. If a second adapter (e.g., LLM-based feedback) appears later, reintroduce the seam — but not before.

Wins

  • ✅ Delete entire delivery_engine/
  • ✅ No hypothetical seam
  • ✅ Feedback logic co-located with scoring
  • ⚠️ Only if no second adapter materializes
⚠ ADR consideration: If ADR-0003 ("separate feedback for future LLM integration") exists, this candidate contradicts it. Worth reopening only if the LLM feedback layer has not materialized after 6+ months and the seam remains single-adapter.

Top recommendation: Candidate 1

The quiz pipeline is the hottest path in the system — every learner interaction flows through it. It currently spans 4 modules with leaky seams, forcing tests to either mock 3 layers or hit the full event stack. Collapsing it into a deep QuizModule gives the highest leverage: one interface for the Router, all implementation details private, scoring logic co-located with session state, and a single module to test.
